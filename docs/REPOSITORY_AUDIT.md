# NEXUS — Repository Audit

Audit of the inherited NEXUS codebase, performed by reading the actual
source (not documentation claims), running the real test suite, and
fixing what was found broken. This is not a rebuild — the codebase was
already substantially real and carefully built; this audit's job was to
verify that claim and correct the gaps it found.

Method: four parallel read-only code audits (DB/isolation, RAG/agent/
approval security, ML/data-science genuineness, frontend fake-data check),
each required to cite `file:line` for every claim, plus hands-on execution
of the backend test suite, frontend build/typecheck, `ruff`, `mypy`,
`pip-audit`, and `npm audit` in this workspace. Every fix below was
verified by re-running the affected tests after the change.

Status legend: **VERIFIED WORKING** (read the code + saw it pass a real
test/run), **PARTIAL** (works but has a caveat worth knowing),
**SIMULATED** (intentionally, and labelled as such in the product),
**FIXED** (was broken, corrected and re-verified in this audit),
**NOT VERIFIED** (not exercised in this environment — stated honestly
rather than guessed).

| SAVEPOINT usage correctness | **FIXED (bug in this audit's own first fix)** | `apps/api/app/services/graph.py::upsert_entity`, `services/ingest.py::_upsert_deadline`, `services/transactions.py::import_transactions` | The first version of the concurrency fix above called `db.add(row)` **before** entering `with db.begin_nested():`. Under a full-suite stress run this produced a *new* failure: `sqlalchemy.exc.PendingRollbackError` on the session's next unrelated `commit()`, because SQLAlchemy only expunges a pending object as part of a savepoint rollback when the `add()` happened *inside* the nested transaction's scope — `add()`-then-`begin_nested()` leaves the object (and the whole session) in a broken state after the caught `IntegrityError`. Reproduced in isolation with a 15-line standalone script before and after the fix to confirm the exact mechanism (not guessed) | Moved `db.add(...)` inside the `with db.begin_nested():` block at all three call sites; re-ran the full suite 25x with exit-code checking (not string-matching) after the fix |
| Background job runner restart safety | **FIXED** | `apps/api/app/tasks/runner.py::JobRunner` (module-level singleton via `get_runner()`) | `stop()` sets `self._stop` (a `threading.Event`) and never clears it. A second `create_app()` lifespan in the *same process* (e.g. a test module building its own `TestClient` after another already did) calls `get_runner().start()` on the same singleton; the new worker threads immediately see `_stop` already set and exit without processing a single job — uploads silently queue forever with no error. Compounded by `db/session.py`'s engine/session-factory singleton: a second app's `init_db()` no-ops if an engine already exists, so it can also silently run against a *different* test module's leftover database. Reproduced deterministically by running `pytest tests/test_e2e.py apps/api/tests/test_concurrency.py` together (order-dependent: passed under the suite's default `testpaths` order, failed with a 30s `TimeoutError` when e2e ran first in the same process) | `JobRunner.start()` now clears `self._stop` and resets `self._threads` so a stopped runner is safely restartable; `apps/api/tests/conftest.py`'s session `client` fixture now disposes/resets the global DB engine before creating its app, mirroring the pattern `tests/test_e2e.py` already used. This was a test-isolation bug, not a production one (a real deployment calls `create_app()`/lifespan exactly once per process) — but it made the test suite's correctness depend on file execution order, which is itself a real defect worth closing |
